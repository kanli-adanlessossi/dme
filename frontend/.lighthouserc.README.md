# Lighthouse CI (`.lighthouserc.json`) — #13 / NFR-11

Garde-fou **INFORMATIF** (ADR-2 de `.kiro/specs/dev-and-ci-tooling/design.md`).
Lighthouse mesure la **vraie** métrique de premier rendu visée par NFR-11
(« premier rendu carte < 3 s en 3G »), mais cette mesure **varie selon la machine
CI**. La rendre bloquante produirait des faux échecs. Lighthouse est donc exécuté
comme **alerte, jamais comme barrière** : il publie un rapport et **ne fait pas
échouer la PR**.

À l'inverse, le budget de bundle (`size-limit`, tâche 5) est déterministe et reste
**bloquant** : les deux se complètent (le bundle empêche la dérive de taille,
Lighthouse surveille la métrique réelle).

## Ce qui est mesuré

- **Cible** : l'accueil (`http://localhost:4173/`) — l'app shell **et** la carte,
  l'artefact critique du premier rendu pour NFR-11.
- **Build de prod servie** : la cible est la build de production (`dist/`) servie
  par `vite preview` (pas le dev server), pour une mesure représentative.
- **Throttling mobile FIXE** : émulation d'écran mobile (360×640) + throttling
  réseau/CPU simulé constant (RTT 150 ms, ~1,6 Mbps, CPU ×4), défini en dur dans
  `.lighthouserc.json`. Fixe = comparable d'un run à l'autre malgré la variance de
  la machine.
- **3 exécutions** (`numberOfRuns: 3`) : lisse une partie de la variance ; le
  rapport agrège les runs.

## Seuils — tolérants, en `warn` (jamais `error`)

Toutes les assertions sont de niveau **`warn`** : elles apparaissent dans le
rapport comme alerte mais ne renvoient **jamais** de code d'échec. Seuils larges,
calibrés pour tolérer la variance CI (perf ≥ 0,5 ; a11y ≥ 0,8 ; FCP ≤ 4 s ;
LCP ≤ 6 s ; TTI ≤ 8 s). Objectif : signaler une dérive franche, pas chicaner sur
le bruit de mesure.

## Exécution

```bash
npm run build   # produit dist/ (Lighthouse audite la build de prod)
npm run lhci     # lhci autorun : démarre vite preview, audite, écrit le rapport
```

Les rapports (HTML + JSON) sont écrits dans `frontend/.lighthouseci/` (ignoré par
git). Prérequis local : Chrome/Chromium installé (vérifiable via
`npx lhci healthcheck`).

## En CI (`.github/workflows/ci.yml`, job `frontend`)

Étape `Lighthouse CI (informatif, ne bloque pas la PR)`, après la build et le
budget de bundle :

- `continue-on-error: true` → un échec éventuel de l'étape **ne fait pas échouer
  le job ni la PR** (double sécurité avec les seuils `warn`).
- Le rapport est publié via `actions/upload-artifact` (artefact
  `lighthouse-report`, rétention 14 j) : consultable sur chaque run sans bloquer.

Le coût (3 runs Lighthouse sur la build servie) reste contenu dans le job frontend
parallèle au backend. S'il s'avère trop lourd sur PR, il peut être déplacé en job
**nightly** (le caractère informatif le permet sans perte de garantie bloquante).

## Version épinglée (L1)

`@lhci/cli` est épinglé à `0.15.0` dans `package.json` (cohérent avec la discipline
du projet : `slowapi==0.1.10`, `maplibre-gl 4.7.1`, `size-limit 11.2.0`), pour
qu'une montée majeure ne change pas silencieusement le comportement de l'audit.
